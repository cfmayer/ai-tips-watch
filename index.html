Article @poteto Nov 18, 2026 Nov 19 edition

Automate Anything with Grok Bot ↗ 6 tips

How Lauren approaches automation: define the goal, describe the process, teach your judgment, give the bot feedback loops, and run it on routines. A reply adds the Dr Eggbot v2 template.

  • Automating anything: start with the goal, not the process. Automation is a goal plus a process. Don't confuse steps (filling a form, sending an email) with the goal; ask what the work is for (revenue, cost) and tell a new bot the goal it's responsible for. If you can't phrase the goal, ask the bot to interview you until you have one you're happy with. #
  • Brain-dump the process, then make the bot restate it before acting. Voice-dictate everything about how you do the job: the usual steps, what you watch out for, the apps and tools used, how you check the work, where the inputs come from, and where feedback comes from. Then ask the bot to restate your goal and process in plain English and not start executing yet. Iterate a few times, then let it connect the tools it needs; optionally ask it to review the process against the goal for a better way. #
  • Teach the bot your judgment with real examples, one question at a time. You make many decisions without noticing (which source to trust when two disagree, when a task is truly 'done'). Feed the bot a few real examples, including ones that went wrong, and ask it to interview you about how you decide, where information lives, how you check work, and when to ask for help, one question at a time, before automating. #
  • Let bots improve themselves by giving them access to feedback. Give the bot the apps and data it needs to find feedback itself (email, social, Google/Yelp reviews) so it can propose process improvements. The more of your business is logged digitally, the better; the bot can even build you a simple app to log events. Consistent unique IDs (customer email, order number, part number) across tools let it cross-reference data. #
  • Use routines so the bot works without you asking. Without a routine, a bot only works when asked. Decide what should trigger the work (an incoming email, a Slack/Teams message, or a schedule) and ask the bot to set up the routine so you stop being the bottleneck. #
  • Install the Dr Eggbot v2 template to design bots for you. Dr Eggbot is a bot designer that creates bots for you. A new v2 template ships with new skills for automating work and life; it differs from the old one, so install v2 fresh and ask the old Eggbot to transfer anything you want to keep. source ↗ #

Thread @ericzakariasson Nov 23, 2026 Nov 24 edition

Editing and refreshing your grok-bot.directory listing ↗ 3 tips

Replies from Eric Zakariasson explaining the new edit and refresh controls for community apps on grok-bot.directory, and how official apps differ.

  • Edit your community listing on grok-bot.directory. Sign in to grok-bot.directory with GitHub (the account that submitted the app), open your submissions and hit Edit to change its name, description, logo and website. A new name or description reruns the security check, so the listing is hidden for a few minutes. If the app isn't in your list, claim it from its page first. #
  • Refresh re-reads plugin.json; set displayName. The directory doesn't pull changes on its own: Refresh in your submissions re-reads your repo's plugin.json and follows renames and moves. To show a friendlier name (e.g. "PR Genie"), add displayName to plugin.json and hit Refresh. source ↗ #
  • Official apps: edit the marketplace's .cursor-plugin/plugin.json. Official apps mirror the marketplace catalog and can't be claimed on the directory. The marketplace reads .cursor-plugin/plugin.json, not .grok-plugin/plugin.json, so change the description there; it syncs to the directory overnight. source ↗ #

15 other kinds of bugs you can tell an agent to look for ↗ 5 tips

Follow-up to Charlie Cheever's implicit-state-machine bug hunt: a 15-post thread of bug classes he found in Exact by pointing an agent at them, each with real examples. Grouped below by theme; each tip names the numbered posts it covers.

  • Bug hunt: timing and ordering (1, 2, 13). Ask the agent to look for: mid-flight cancellation and teardown (async work cancelled, closed or unmounted before it finishes); out-of-order events (a late reply, retry or event clobbering newer state); and check-then-act (a precondition checked, then acted on after something underneath changed). source ↗ #
  • Bug hunt: safety bypasses (3, 6, 14). Ask the agent to look for: back doors (a secondary path that walks around your safety checks); trust boundaries (data from a file, URL, network or save state trusted without validation, e.g. javascript: URLs in hrefs, unvalidated refs passed to git fetch); and fail-open defaults (missing config, an unexpected exit code or unknown status silently treated as allowed or passed). source ↗ #
  • Bug hunt: state that drifts (4, 7, 8). Ask the agent to look for: two sources of truth (stored and cached copies that drift apart); halfway failure (a multi-step write that fails partway and leaves state half-mutated or wedged); and asymmetric pairs (encode/decode, export/import, validate/execute quietly drifting apart). source ↗ #
  • Bug hunt: input limits and encoding (5, 9, 12). Ask the agent to look for: quadratic work, stack depth and allocation (unbounded recursion, O(n^2) loops, giant allocations from nested or hostile input); boundaries (zero, empty, max-size or off-by-one inputs); and numeric narrowing, Unicode and escaping (silent integer truncation, unescaped raw text, coercion bugs at format seams). source ↗ #
  • Bug hunt: wiring gaps and tests that lie (10, 11, 15). Ask the agent to look for: copy-paste drift (a fix landed in one near-duplicate copy but not the other, e.g. macOS but not iOS); dropped plumbing (a flag, scope, kind or init hook left off when wiring a new path or target); and bypassed tests (a test that can silently skip its check or bail early). source ↗ #
