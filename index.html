Grok Bot @poteto Nov 18, 2026

Automating anything: start with the goal, not the process

From the article 'Automate Anything with Grok Bot': automation is a goal plus a process. Don't confuse steps (filling a form, sending an email) with the goal; ask what the work is for (revenue, cost) and tell a new bot the goal it's responsible for. If you can't phrase the goal, ask the bot to interview you until you have one you're happy with.

Grok Bot @poteto Nov 18, 2026

Brain-dump the process, then make the bot restate it before acting

From the same article: voice-dictate everything about how you do the job: the usual steps, what you watch out for, the apps and tools used, how you check the work, where the inputs come from, and where feedback comes from. Then ask the bot to restate your goal and process in plain English and not start executing yet. Iterate a few times, then let it connect the tools it needs; optionally ask it to review the process against the goal for a better way.

Teach the bot your judgment with real examples, one question at a time

You make many decisions without noticing (which source to trust when two disagree, when a task is truly 'done'). Feed the bot a few real examples, including ones that went wrong, and ask it to interview you about how you decide, where information lives, how you check work, and when to ask for help, one question at a time, before automating.

Let bots improve themselves by giving them access to feedback

A prompt to evaluate any new technology against your codebase

Prompt of the day (using the XState v6 beta): 1) research what it does and the problem it solves; 2) find the gnarliest problem in our app it might help with; 3) build a proof of concept in a draft PR; 4) fully verify the results; 5) grade it on API nuance (more is worse; agents do better with fewer choices), type safety, testability, added cyclomatic complexity, docs quality, and deployment changes; 6) give an overall recommendation. Code quality @poteto Nov 14, 2026

Turn every agent correction into a deterministic check

Your codebase is one of the agent's biggest inputs. When you correct an agent, try to make it a lint rule, type or test rather than another line in your rules or AGENTS.md: it's reproducible and enforceable. Anti-patterns and tech debt get copied by the next agent, so keep the codebase as pristine as possible.

Code quality @dexhorthy Nov 14, 2026

Keep reviewing something: plan, design, or result

From the No AI Slop Manifesto (slopmanifesto.com), co-written at AIE Code Summit: AI amplifies human judgment rather than replacing it; we own the intent, taste and consequences of what we ship; and there will always be value in reviewing something. Even if we stop reading most code, review the plan, design or result, or you get the same output as everyone else. The right level of review depends on the stakes.

Code quality @poteto Nov 14, 2026

Quick fixes considered harmful: ask agents for the root-cause fix

Asking an agent for the smallest or quickest change can make it write worse code: the bandaid becomes a pattern the next agent copies until it spreads everywhere. We used to accept bandaids because time was short; agents change that calculus, so sometimes ask for the root-cause fix even if it's more invasive.

Generate property-based tests from both the spec and the code

Endorsed by @GeoffreyHuntley ('taps sign'), from @eulerfx: in a paper across 25 agent-built apps, spec-driven property-based tests found 56 bugs that code-driven ones missed, and code-driven found 43 that spec-driven missed (59% of bugs found by only one approach). Setup: an agent writes invariants in plain English from the requirements, then turns them into property tests by reading the code. Use both.

Five tools to measure and improve agent throughput

1) Online evals and LLM-as-judge scorers on past runs (e.g. 'is it writing redundant tests?'); 2) self-improvement loops that mine eval results for factory changes; 3) benchmarks that rerun tasks under different configs; 4) model routing based on those results; 5) A/B tests to prove changes going forward.

What a factory's orchestration layer must do

Once foundations are in code, orchestration should: read the code at the current version (or an experiment branch); spin up the right sandbox on demand; route work to agents with the right model and harness; prompt them per the factory code; store artifacts and traces; loop in humans who can hand off or steer; and integrate with Sentry, GitHub, Jira, Slack, etc. Think Terraform, but for agents.

Software factories @zachlloydtweets Nov 13, 2026

The software factory stack, layer by layer

00 factories-as-code (workflows, permissions, sandbox config all versioned); 01 own your data and context (skills, MCPs, traces, logs); 02 compute: agents get their own sandboxed, self-hostable computers; 03 inference: any model and harness, no lock-in; 04 improvement: observe cost per PR, cycle time and DORA metrics, with agents scoring output and proposing changes; 05 orchestration: launch, track, recover, pass messages; 06 access: MCP server/REST API and integrations (Slack, Teams, Jira, Linear) rather than a tightly coupled web 'ADE'.
